SGLang Self-Pause 实现方案

面向“并发推理期间 SIGKILL 一个 DP rank”的硬故障：故障即 pause，废弃全部在途请求， 不续推；pause 阶段中断设备，scale-down 阶段恢复设备并重建通信域。

目标策略：Pause & Discard 故障类型：Hard SIGKILL 执行后端：NPU MC2 / HCCL 测试负载：concurrency = 10
目录 1. 整体流程 2. Pause 语义 3. 当前问题 4. 目标架构 5. 故障处理时序 6. 代码改动方案 7. 正确性约束 8. 验收标准

1. 整体流程

故障检测 → Pause → 清理 → Scale-down → 恢复
  1. 检测到 DP rank 退出，集群进入 PAUSING。
  2. 拒绝新请求，并结束故障时仍未完成的请求。
  3. 中断存活 rank 上的 MC2/HCCL 执行，清理 batch 与 KV cache。
  4. 收齐存活 rank 的 PAUSED ACK 后执行 scale-down。
  5. 恢复设备、重建通信域、更新 active mask，最后恢复服务。

关键前提：pause 的设备中断不能依赖普通 Scheduler event loop。 Scheduler 可能正阻塞在 TBE/MC2 调用中，必须由独立的控制路径触发 HCCL abort 或 stop_device，让执行线程真正返回。

2. Pause 语义

请求层

  • 进入 pause 后，所有新请求直接返回 503。
  • 故障发生时仍未完成的请求，由 Tokenizer 统一终止为 503。
  • 迟到的旧 Scheduler 输出按 incident epoch 丢弃。

执行层

  • 存活 rank 停止当前设备执行，清空 batch、结果队列和 KV cache。
  • 被 kill rank 的设备资源由进程退出回收。
  • scale-down 后不恢复旧请求，只接收新请求。

Tokenizer 必须参与请求清理，因为被 SIGKILL 的 Scheduler 无法再发送 AbortReq； Scheduler 则负责清理存活 rank 上的执行状态和 KV cache。

3. 当前问题

当前由进程退出触发的 pause 只会拒绝后续请求，不会主动处理执层的在途请求。 现有 discard 仅在 MC2/HCCL 算子异常冒泡到 Scheduler FT event loop 时执行。

4. 目标架构

故障处理由控制层发起，执行层完成设备中断和本地资源清理。控制器以 incident epoch 记录一次完整故障处理过程，并通过 ACK 确保所有存活 rank 清理完成后才进入 scale-down。

NPU/HCCL 在途请求清理路径

初始： active_ranks = [1, 1, 1, 1] last_active_ranks = [1, 1, 1, 1] kill rank 3 ↓ 幸存 rank 上正在执行的 MC2/HCCL 算子检测到通信异常 ↓ 算子向 Scheduler 抛出异常 ↓ Scheduler 捕获异常并向 DPC/FT 控制器上报 PauseIncident 上报中的 rank 只是 reporter_rank（异常上报者） ↓ DPC/FT 控制器确认“发生了 DP 通信故障” 将 reporter Engine 的服务状态记为 UNHEALTHY，但不把它当作被 kill 的 rank ↓ 控制器创建 incident epoch，并将集群状态切换为 PAUSING ↓ Tokenizer 拒绝后续请求，并记录需要废弃的在途请求 ↓ 控制器通过独立控制路径向所有已配置的 DP Engine 广播 pause/status 探查 ↓ 已从算子返回的 Scheduler 直接进入清理 仍阻塞在设备算子中的幸存 rank 执行 HCCL communicator abort 或 stop_device ↓ 其余正在执行的 MC2/HCCL 操作被中断 ↓ ModelRunner / Scheduler 从设备调用返回 ↓ _ft_discard_inflight_window() ↓ 释放幸存 rank 的 KV cache 清空 running_batch / last_batch / result_queue ↓ Tokenizer 将全部在途请求结束为 503 ↓ 幸存 Scheduler 返回 PAUSED ACK ↓ Scheduler self-pause，将本 Engine 标记为 UNHEALTHY，不继续调度 ──────────── 存活探查与恢复决策 ──────────── DPC/FT 控制面查询每个已配置 Engine 的状态 ↓ rank 0 / 1 / 2 响应 UNHEALTHY/PAUSED：进程存活，可恢复 rank 3 无响应，且 DPC 进程监控确认退出：DEAD ↓ 全部预期 rank 均存活时可对 UNHEALTHY Engine 执行 retry 存在 DEAD rank 时对其执行 scale-down，对幸存 Engine 执行恢复 ──────────── scale-down 恢复阶段 ──────────── 控制器收齐全部 PAUSED ACK ↓ active_ranks = [1, 1, 1, 0] ↓ restart_device ↓ 按 active_ranks 重建 HCCL 通信域 ↓ 更新 MC2 metadata、执行 EPLB ↓ 发布新的 route mask ↓ 解除 pause，恢复接收新请求 核心区别： Mooncake 通过通信层更新 active_ranks 来触发异常； NPU/HCCL 首先通过算子异常触发 pause；如果部分幸存 rank 仍阻塞在设备执行中， 再由控制层通过 stop_device 使这些 rank 返回到 Scheduler。 所有幸存 Engine 都进入 UNHEALTHY/PAUSED；具体故障 rank 由 DPC 状态探查结合进程存活检测确认。 与 vLLM 的对应关系： vLLM 存活 Engine 自标记 UNHEALTHY = SGLang 存活 Scheduler self-pause vLLM 外部编排器逐个查询 = SGLang DPC/FT 控制面广播 status 并结合进程监控 vLLM 对可恢复实例发 retry = SGLang FT Manager 对存活 Engine 发 retry/scale-down 恢复命令 实现注意： 当前 FaultToleranceRankFaultOutput(rank=self.ps.dp_rank) 中的 rank 是捕获异常的幸存 rank。 将它加入 unhealthy_dp_ranks 可以表示“该 Engine 仍存活但不可服务”，不能用来推断谁被 kill。 控制面还应通过广播 pause 使其他幸存 Engine 也进入 UNHEALTHY/PAUSED， 并单独用 process_alive 或心跳结果表示 DEAD。
1

异常触发

幸存 rank 的 MC2/HCCL 算子抛出通信异常；Scheduler 自标记 UNHEALTHY 并上报 PauseIncident，但该 rank 只是报警者。

2

进入 Pause

FT 控制器创建 incident epoch，广播 pause；所有响应的 Engine 进入 UNHEALTHY/PAUSED，Tokenizer 拒绝新请求。

3

中断并清理执行层

独立控制路径中断存活设备上的 MC2/HCCL；Scheduler 随后清理 batch、结果队列和 KV cache。

4

故障定位与恢复

DPC 逐个探查 Engine 状态；响应 UNHEALTHY/PAUSED 的为存活实例，无响应且进程退出的为 DEAD，再选择 retry 或 scale-down。

设备中断接口

DeviceFaultInterrupter.pause(epoch) 1. 幂等检查：同一 epoch 只执行一次 2. 向所有已配置的 DP Engine 发送 pause/status，收集可达实例的响应 3. 优先调用 HCCL communicator abort / 异步故障接口 4. 若后端只提供 stop_device，则通过独立且已验证安全的控制线程调用 5. 等待执行线程从 MC2/TBE 返回 6. 通知 Scheduler 执行本地状态清理

如果 TorchNPU 明确要求 stop_device 必须由 ModelRunner 的 device-owner 线程调用， 就不能简单从 DPC 进程调用它。此时需要 HCCL 的异步 abort 能力，或者调整执行线程模型： 保留一个可响应控制命令的设备拥有者，由工作线程承担可能阻塞的 forward。

5. 完整故障处理时序

T0 · 推理正常运行
并发请求已经分配到多个 DP rank，部分请求处于 prefill/decode。
T1 · SIGKILL 一个 DP rank
受害进程瞬间退出；其设备上下文和 KV 资源由进程退出回收。
T2 · MC2/HCCL 算子抛出异常
幸存 Scheduler 捕获异常，将自身 Engine 标记为 UNHEALTHY 并上报 PauseIncident；该 rank 是 reporter，不等于被 kill 的 rank。
T3 · Tokenizer 全局 pause
新请求立即返回 503；故障时仍未结束的请求由 Tokenizer 统一完成为 503。
T4 · 中断存活设备
通过不依赖 Scheduler event loop 的路径执行 HCCL abort 或 stop_device。
T5 · Scheduler 清理并 ACK
所有响应 pause 的 Scheduler 清空 running/last/current/result_queue/chunked request，释放 KV，以 UNHEALTHY/PAUSED 状态停止调度。
T6 · DPC 探查 Engine 状态
逐个查询所有已配置 Engine；响应 UNHEALTHY/PAUSED 的为可恢复存活实例，无响应者再结合进程退出或心跳租约确认为 DEAD。
T7 · 控制器选择恢复动作
全部预期 rank 存活则可 retry；存在 DEAD rank 则对其 scale-down。仅在存活 Engine 全部 PAUSED 后进入 RECONFIGURING。
T8 · restart 与通信域重建
restart_device，重建图外 HCCL group，更新 MC2 metadata/active mask，并执行 EPLB。
T9 · 恢复服务
所有存活 rank 返回 READY ACK 后发布新 route mask，状态回到 RUNNING。

6. 代码改动方案

模块修改内容性质
fault_tolerance/controller.py 增加 incident epoch 与 RUNNING/PAUSING/PAUSED/RECONFIGURING 状态；分离 Engine 服务状态与成员存活状态：unhealthy_dp_ranks 表示存活但已 pause 的 Engine，process_alive_* 表示 HEALTHY/UNHEALTHY 与 DEAD 的边界。 必须新增
fault_tolerance/manager.py 收到算子异常后立即发起全局 pause，广播并收集每个 Engine 的状态；全部预期进程存活时允许 retry，有 DEAD rank 时转 scale-down；pause 超时时 fail-stop。 需要调整
managers/io_struct.py 将算子异常事件定义为 FaultTolerancePauseIncidentOutput，包含 reporter rank 和错误信息；新增带 epoch、Engine 状态和清理结果的 FaultTolerancePauseReq/Output，不在事件中把 reporter 表达为 failed rank。 必须新增
managers/tokenizer_manager.py 原子切换至 pause；快照故障窗口内的请求；将所有未完成请求终止为 SchedulerFault/503；防止旧 epoch 输出污染恢复后的请求。 必须新增

7. 正确性与安全约束

  1. 顺序约束：先 pause/stop/clean，再 restart/rebuild/route；不得交叉。
  2. 状态分离：UNHEALTHY/PAUSED 表示 Engine 仍存活但不可服务；只有进程退出或心跳租约失效才可确认 DEAD，不能仅凭单次探查超时判死。
  3. ACK 屏障：DPC 完成存活探查并固定 survivor 集合后，没有收齐该集合的 PAUSED ACK，不能开始 scale-down/retry。
  4. 幂等：stop、清理、restart 和 ACK 都以 incident epoch 去重。
  5. 超时策略：任何 survivor 无法 pause 或清理时执行 fail-stop，不允许带着未知通信状态恢复。
  6. 路由原子性：新 route mask 只能在通信域和 MC2 metadata 全部就绪后发布。
  7. 线程安全：正式采用独立线程调用 stop_device 前，必须验证 TorchNPU 对调用线程及设备上下文的约束。

8. inflight_scale_down 验收标准

测试场景保持不变：并发度 10，持续推理过程中 SIGKILL 一个 DP rank，随后执行 scale-down。

  • 故障检测后，新请求全部返回 503，直到恢复完成。
  • 故障窗口内未完成的请求在限定时间内全部终止，不允许客户端超时。
  • 在途请求终态为 503/SchedulerFault，traffic_errors == 0。
  • 所有存活 Scheduler 日志包含同一 epoch 的 pause、discard 与 ACK。
  • 恢复决策前，状态探查显示幸存 Engine 为 UNHEALTHY/PAUSED，被 kill rank 经进程存活检测确认为 DEAD。
  • scale-down 前至少一次 device stop；恢复阶段包含 restart 和通信域重建。
  • 无额外 TBE 进程退出、无 survivor 崩溃、无永久阻塞。
  • 恢复后的新请求返回 200，输出与故障前基线一致。
  • 连续执行多轮故障注入仍满足以上条件，无残留请求或旧 epoch 输出。
需要收紧现有测试：当前测试记录了 traffic_errors，但没有断言其为零。 最终测试必须区分“故障前已经完成的 200”和“故障时仍在途的请求”，并明确断言后者全部收到 503， 否则偶然超时也可能被报告为 PASS。
