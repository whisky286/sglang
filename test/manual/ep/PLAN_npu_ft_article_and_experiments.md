### 请求重试的表述

控制面的 `retry` 表示尝试恢复当前拓扑上的引擎执行。请求重试表示将某条逻辑请求重新派发。上层需要结合失败原因、旧执行状态、是否已交付输出、剩余期限和健康容量决定请求的后续动作。

容量不足适用延后或有余量的目标；执行结果不明时需先查询或依赖服务端去重；流式已交付内容的请求需要续推协议。主实验中客户端自动重试关闭，每个逻辑请求发起一次 HTTP 尝试。故障后的自动请求重试与流式续推按后续实现另设实验。重试预算的设计依据可参考 [Google SRE](https://sre.google/sre-book/addressing-cascading-failures/)。

## 4. 实验安排

### 实验 1　故障后缩容接单与整实例重启

假设为局部故障后，缩容可以更早恢复一部分服务能力。A 组在确认 incident 后重启整个四卡实例，B 组在相同判定点下发 `scale_down` 并保持健康三卡。A 组完成恢复时使用四卡，B 组首次完成恢复时使用三卡，图表标注当时成员数。

两组预热后，以同一固定到达时间表持续发请求，在同一逻辑触发条件下注入 rank 1 进程退出。触发条件为一条定向 rank 1、输出上限 1536 token 的独立长请求已经交付至少 256 token。主负载与该定向请求分别标记。复用相同的 incident 观察规则和控制触发方式。

恢复策略由单一 Shell 驱动在首次确认 incident 后触发，登记轮询间隔和命令开始时间。人工触发的结果须登记人工等待时间，并单独呈现。主负载在恢复期间持续产生请求，服务端拒绝与客户端连接失败均保留。

共同观察窗口从故障注入起持续 600 秒，两组比较该窗口内的成功、拒绝、abort、连接失败和超时。超出窗口仍未恢复的轮次记为 `>600s`。窗口内发出的请求按各自截止时间补收终态。

主要结果为故障到首次新请求正常完成的时间及失败请求数，同时展示检测、控制等待和恢复执行的分段耗时。B 组后续补回四卡的时间单独统计；为采集三卡稳态而主动等待的时间另行记录。

### 实验 2　降级吞吐、达标容量与回归表现

比较故障前四卡、实际故障缩容后的健康三卡、补回原 rank 后四卡。固定模型、输入、输出长度、采样、缓存及调度限制。

先以一档共同负载比较三阶段的正常输出吞吐和时延，再逐档提高发包速率，找到三卡和四卡各自第一档不达标的负载。预试从能够稳定完成的低速率开始，逐次翻倍；找到边界后在相邻两档中间加点。正式使用的绝对请求率清单在预试后冻结，三阶段执行同一清单。

发包采用固定到达时间表，按设定请求率发送。登记计划发送时间与实际发送时间，确认客户端排队和并发限制没有把负载压低。每档使用独立的稳态窗口，预热和上一档积压清空后开始。

每个正式稳态窗口至少 120 秒，并尽量获得至少 200 条正常完成样本；单档采集最长 600 秒。达不到样本要求时保留原始结果和样本数，标明 P95 样本不足。达到截止时间仍无法排空的档位记为不达标。

有厂商业务 SLO 时采用预先提供的阈值。首轮无业务 SLO 时，使用四卡轻载参考运行的 P95 首 token 时延和 P95 每 token 平均耗时，各乘 2 得到实验门槛；参考值、倍数和绝对门槛在正式实验前冻结。一个负载点达标需要正常完成率至少 99%，且两项 P95 都在门槛内。该门槛描述本实验的比较条件。

主要报告共同负载的输出 tokens/s，以及最高达标发包速率。容量保留率等于三卡最高达标请求率除以四卡最高达标请求率。采样网格给出最大已验证点和首个不达标点。四卡回归率以补回后的四卡与故障前四卡在同一负载下的结果相除。

### 实验 3　主动补卡对已有请求与新接入的影响

A 组在健康三卡上运行长流并保持三卡。B 组在同样状态下运行相同长流，在客户端首次观察到累计至少 256 token 的事件后发起 `recover`。长流输入分词后固定为 256 token，输出上限 1536，忽略 EOS；客户端期限为 900 秒。记录触发时实际累计 token 数和剩余输出量。

恢复排空期间每秒发送一次独立接入探针。已有长流统计最终状态、实际输出量、完整生成耗时和最长无新输出间隔。接入探针统计拒绝起止时间与数量。恢复后检查四卡状态、PID、创建时间，并向回归 rank 发送真实生成请求。

另做排空超时用例。在有长流运行时，以 1 秒排空期限触发恢复，检查 408 与可识别原因、成员版本和 PID、长流继续输出以及健康三卡恢复新接入。该用例预期得到明确超时；验证完毕后单独进行正常补卡。

记录排空等待、排空后成员恢复与新接入关闭三个时间段。排空后的成员恢复耗时包括进程启动、权重准备、通信安装、验证和路由恢复。需要进一步归因时，再对这些内部阶段增加可核验事件。

## 5. 指标和统计口径

### 时间与成功终态

所有客户端耗时由同一计量进程的单调时钟计算。故障注入、策略触发与控制请求写入同一时间轴。服务器日志与客户端时间用于跨进程关联时记录时钟偏差和日志精度，跨机器先校时。

| 事件或指标 | 定义 |
|---|---|
| `t_fault` | 实际发送结束 rank 进程信号的时刻，随后核实目标退出 |
| `t_incident` | 计量端首次观测到控制面确认 incident 的时刻；登记轮询间隔 |
| `t_action` | 计量端开始提交恢复策略的时刻 |
| `t_service` | 目标成员状态提交之后发起的第一条成功探针完整生成结束时间；A 为重启后的四卡，B 为缩容后的三卡 |
| 故障到接单恢复 | `t_service - t_fault`。探针每秒一次，保留完整发送与终态记录 |
| 检测与控制等待 | 分别为 `t_incident - t_fault` 和 `t_action - t_incident` |
| 策略执行到真实生成 | `t_service - t_action`，包含探针到达间隔和生成耗时 |
| 补卡排空等待 | 服务端同一时钟中排空开始至确认排空完成的时间 |
| 排空后恢复 | 排空完成至回归 rank 首次成功生成的时间，按可关联的时钟计量 |
| 新接入关闭窗口 | 接入门禁关闭至重新开放的区间；每秒探针给出观测范围与采样误差 |
| 首 token 时延 TTFT | 客户端发出请求至收到第一个有实际 token 增量的事件 |
| 每请求平均 TPOT | `(最后一个 token 到达时间 - 第一个 token 到达时间) / (实际输出 token 数 - 1)`，至少输出两个 token |
| 最长无输出间隔 | 相邻实际 token 增量事件之间的最大间隔，另记最后输出到终态的等待 |

正常完成需要在期限内取得预期终态、有效非空输出及一致的 token 计数。固定长度请求还需要达到目标输出量并以 length 正常结束。abort、SSE 错误、连接中断、超时及终态缺失分别保留。`ignore_eos` 的固定长度输出用于执行负载控制，内容质量另用少量确定性输入核对。

服务恢复探针使用固定短输入、temperature=0、输出上限 16 token、忽略 EOS，固定每秒发送一次、单条期限 10 秒。探针输出和流量独立记录，并纳入负载预算。关联成员提交事件需要保存服务端时间与时钟偏差，样本位于时间精度不确定区间时，采用之后能够确认的首条探针。

### 吞吐、容量与请求分母

整个服务的有效输出吞吐为测量窗口内交付、且所属请求最终正常完成的输出 token 数，除以窗口实际秒数。按客户端收到 token 增量的时间归桶，跨窗口长请求只贡献该窗口内收到的部分。输入 token、预热、健康探针和独立故障触发长流分别标记。每秒原始输出量可以另画曲线，并注明其中来自最终失败请求的部分输出。

SSE 一个事件可能包含多个 token，按累计 completion_tokens 的增量统计。各卡吞吐合计为实例吞吐。每卡平均值如需展示，另除以当时活跃卡数并注明单位。

请求完成率按发送时间选取请求集合，再等待其终态至截止时间。分母包含该集合内所有真正发出的请求，连接失败、503、abort 和超时均占分母。计划发出却被压测客户端延迟的请求单独登记。主负载每请求期限暂定 120 秒，预试确认后冻结；所有重发沿用原期限。

请求结果按正常完成、接入拒绝、流式或服务端 abort/错误、传输失败、截止时间到达、人工取消归类，每次 HTTP 尝试只有一个最终类别。保存 HTTP 状态和服务端原因，供进一步细分。到达截止时间前已被显式拒绝或失败的请求使用其已知类别。

P95 TTFT 和 P95 TPOT 在正常完成样本中分别计算，每项同时报告样本数。失败率和迟到终态单列。可选的请求 goodput 为符合预定单请求时延要求且正常完成的请求数除以测量时间，其门槛与窗口归属需单独写明。

三类请求分别呈现结果。故障注入前已经产生输出的请求为故障在途请求，恢复期间按时间表新发出的请求为新接入请求，三卡健康后为补卡排空而接入的长流为主动恢复在途请求。

### 采集工具与当前缺口

当前 [`async_request_sglang_generate`](../../../python/sglang/benchmark/serving.py) 在 HTTP 200 的流正常读完后将 success 置为 true，未将最终 abort 作为失败判定条件。文章实验需保存并核对原始 SSE 最终事件。该计量适配列为前置任务。

## 6. 重复、原始数据与图表

先做一轮预试，确认两种恢复策略、所有计量事件和客户端成功判定均可用。正式实验 1 和 3 各做 5 对独立重复，交换 A/B 顺序，并为每轮启动干净实验实例。实验 2 对同一负载网格做 5 轮三阶段采集。另在同一服务连续故障与恢复两轮，检查成员版本和缓存资源能否继续工作，作为稳定性补充。

恢复耗时保留每轮数值，报告成功轮数、失败原因、中位数和最小至最大范围。5 轮结果用于观察重复性。请求分位数按各轮请求计算；如汇总多轮样本，同时保留逐轮统计和每轮样本量。

| 原始文件 | 最少内容 |
|---|---|
| `manifest.json` | run/config/round/arm 编号、时间、代码 SHA、工作树差异、硬件软件、启动参数、模型/请求集合校验值、速率、截止时间、实验门槛、开关 |
| `events.jsonl` | 故障信号、incident 观测、策略提交与返回、成员提交、排空开始与完成、路由恢复、探针发送与完成 |
| `requests.jsonl` | 请求 ID、所属集合、计划/实际发送时间、首末 token、终态时间、实际输入输出量、HTTP 状态、finish_reason、错误、期限 |
| `streams/` | 每条流的原始 SSE、token 增量时间、curl 退出码与 stderr，敏感输入采用合成数据 |
| `server.log` 和状态快照 | 原始日志、各阶段状态与成员版本、完整控制响应、每阶段实际 KV 和调度限制 |
| `processes/` | 每阶段 PID、PPID、进程创建时间与角色；故障注入前核实本轮目标 |
| `summary.json` | 每轮指标、失败轮及采集异常，能够追溯到原始文件 |

每轮目录独立保存，原始文件留存于实验机器，再按索引回传。计量数据与字段是本计划需要交付的格式。各轮完整命令、环境、退出状态和原始日志随结果保存。
