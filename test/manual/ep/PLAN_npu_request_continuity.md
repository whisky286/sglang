## 1. 目标、首版范围与完成定义

目标是让符合条件的在途请求在成员恢复成功后继续完成，客户端不必 Ctrl+C 再重发。集群缩容、补卡仍沿用运维手动 apply；本方案增加自动请求恢复，不自动选择或结束其他进程。

| 场景 | 目标行为 |
|---|---|
| 健康三卡主动 recover 到四卡 | 先完成已有请求，再切换成员；正常请求不因 recover 被主动结束 |
| 故障导致正在生成的请求中断 | 保留原 HTTP 等待，缩容提交后自动重试或接着生成 |
| 客户端取消、超过恢复期限、不可恢复错误 | 明确结束并清理；不再复活或无限等待 |
| 新请求在成员变更期间到达 | 首版明确返回现有 503；避免无界排队和接入竞态 |

首版继续使用成功环境：单机 NPU MC2、普通非 PD 部署、关闭执行图与 overlap。模型使用已确认的 DeepSeek-V2-Lite-Chat；TP/DP/EP=4、ops/dynamic、128 冗余等沿用已提供的完整手动命令，完整生效参数与包元组仍需在新实验保存，不把计划参数当作已逐项实测。

先支持纯文本、单请求单候选、temperature=0、默认惩罚参数、EOS/长度停止。第一批接口为 /generate 非流式，再覆盖 /generate 流式和 /v1/chat/completions 普通文本流式。自定义 stop、采样、logprobs、grammar/工具/推理解析、session、LoRA、多模态、批量多候选和硬绑定已失效 routed_dp_rank 不承诺透明恢复；开启恢复策略时在接入阶段明确校验，不能默默采用错误语义。其他组合之后逐项增加。

HTTP/Tokenizer/Detokenizer 控制进程与原连接持续存活是首版前提。HTTP 进程崩溃、客户端断线重连后的跨连接恢复，需要持久化记录与确认协议，是后续独立能力。

完成定义：成员恢复成功、请求未取消/超时且属于支持范围时，原请求最终完成；普通请求只返回一次最终结果，流式输出保留已有前缀并只增加后续内容。失败时有明确、有限时间内可见的终态。

## 3. 统一请求记录：保存什么、谁负责

在 TokenizerManager 所在的存活进程新增独立 RequestRecoveryCoordinator/RequestJournal。大类仅保留接线、事件转发和状态赋值，重试策略与重建规则放在 fault_tolerance 独立模块中；ModelRunner 不承载请求日志。

每个逻辑请求保存以下 CPU 状态，不读取故障设备上的 KV 或张量：

| 状态 | 用途 |
|---|---|
| 不变的公开请求 ID、规范化 tokenized 输入、模型/权重版本 | 重新构造原请求，避免重复聊天模板、BOS 或文本重新分词 |
| 生成参数、原长度上限、停止配置、原始输入长度 | 恢复后保持请求语义和统计 |
| 当前内部 attempt_id、派发 membership_epoch | 区分同一请求的多次执行，拒绝旧输出与旧 Abort |
| 接收顺序号、执行 rank（允许未知）、是否已发 Scheduler | 覆盖首次输出前故障和异步接入竞态 |
| 已提交 token 前缀、解码增量记录、已排队/已交给 HTTP 的输出游标 | 恢复计算和流式输出，避免重复或遗漏 |
| 绝对 deadline、额外重试次数、取消/终态 | 有限恢复、不复活已取消请求、只结束一次 |

登记顺序必须是“保存逻辑请求 → 保存规范化输入 → 发送执行请求”。不能等收到第一 token 后才保存，否则故障卡没有发出任何输出时仍会丢请求。控制层已接收但尚在 tokenize/发送队列中的请求同样纳入管理。

状态迁移：接入 → 执行中 → 故障暂停 → 等待成员提交 → 新尝试执行 → 完成；任何非终态均可转取消或明确失败。完成、取消和失败均不可逆。第二次故障从新的 attempt 再走同一流程。

## 4. 协议隔离：旧结果不能污染新尝试

保留公开 rid，新增内部 attempt_id；不要把“重试次数”混成集群 membership_epoch。一个 epoch 内也可能重新派发请求。

TokenizedGenerateReqInput、Scheduler 内部 Req、BatchTokenIDOutput、BatchStrOutput、AbortReq 和取消/排空消息传递相同身份；批输出按每条请求对齐。成员版本、attempt_id 与每次输出的序号/token 区间共同校验。普通未开启恢复的请求保留兼容默认值；已开启恢复的尝试不能在缺少必要身份时误接收旧消息。

必须在两个位置拦截：

1. Detokenizer 修改 decode_status 之前，避免迟到 token 先改变解码状态。
2. Tokenizer 修改 RequestJournal、ReqState、out_list 或 finished 之前，避免旧 Abort 结束新尝试。

故障冻结当前 attempt 后，不再提交该 attempt 的新结果。完成若在冻结前已经提交，就保持完成；冻结后到达的旧终态按旧尝试处理。已取消请求记录有限期 tombstone，收到旧完成也不能恢复。身份与序号还要覆盖延迟的取消、重复结果和重复控制 ACK。

## 5. 主动扩容：先排空，再切换

流程为“关闭新请求入口并确定接入边界 → 让已有请求正常运行 → 全体确认排空 → 原有 pause/prepare/validate/commit → 开放入口”。

排空不能只看 running_batch：需要包括等待队列、chunked 请求、结果队列、异步 tokenize、DPC 已接收未转发请求，以及前端尚未提交的终态消息。接入关闭前已经登记的请求允许完成，之后的新请求首版返回明确 503。

排空期间 Scheduler 的正常前向与控制循环继续运行，不能提前置 engine_paused，也不能让 DPC 阻塞在等待 ACK 中；不能持有阻止旧请求完成或控制消息处理的锁来等待排空。只有全部幸存 Scheduler 在 batch 边界确认本地无剩余任务，且前端接入边界内的请求均有终态，才进入原来的通信组切换。切换前仍执行健康设备同步，不能仅凭前端请求数为零判断设备空闲。

排空超时且旧组仍健康：返回可识别的排空超时，解除入口限制，继续三卡服务；不进入 prepare，不调用现有 apply 异常的整体 fail-stop。若期间发生真实故障：终止本次主动扩容准备，保留故障暂停，释放操作锁以允许后续 scale_down；不能误恢复入口。通信域已经开始切换后的失败继续采用现有 fail-stop 边界，不承诺回滚旧组。

## 6. 故障缩容后的请求恢复

故障通知、可恢复 Abort、进程退出三种事件均可触发冻结，不能依赖坏卡发出“我有哪些请求”的通知。首版按受影响 EP 成员版本冻结未完成请求，再用终态/序号核对去重；不能只恢复已知属于坏 DP rank 的请求，因为 EP 集体故障也会中断幸存者上的请求。

本地 Scheduler 仍清理坏批次、句柄与 KV 引用；恢复前不能安全释放的设备状态沿用当前 deferred release 规则。对可恢复请求发送内部暂停/脱离尝试通知，前端保留请求记录与原 HTTP 等待。不将这类通知直接转成最终 503。用户取消、参数错误、不可恢复错误与未启用恢复的请求继续明确终止。

运维执行 scale_down 后，等待健康检查和路由提交成功，再统一选健康成员、按并发/内存预算重派发。恢复队列优先，避免一次性大量重新 Prefill 导致 OOM；固定 routed_dp_rank 已失效时不能默默改写用户绑定，首版不支持此类透明迁移。

两步实现：

**非流式先行。** 客户端尚未拿到内容时，可以从原 tokenized 输入重新计算一次，使用新的 attempt_id，清理旧的未公开聚合状态，公开请求 ID 和原 deadline 不变。只返回一次最终响应；额外计算计入恢复指标，最终 completion_tokens 不叠加失败尝试。

**流式接着生成。** 设原输入为 P、前端已提交的输出 token 为 G。新请求重建全新 KV，重新计算 P+G 后生成后缀。必须保留“原输入 P”和“已生成 G”的语义边界；不能简单把 P+G 当作新 prompt 调用普通接口，否则生成长度、惩罚、停止条件和用量统计都会改变。可借鉴现有 retract/re-prefill 机制，但不复用故障设备上的 Req、内存指针或旧 dispatcher handle。

恢复构造器负责原输入长度、output_ids、fresh KV 的填充、decode/输出起点和长度上限。已提交 100 tokens、原上限 1536 时，总输出仍以 1536 为上限。已满足 EOS/长度的请求直接按终态收尾，不额外采样一个 token。第一批只支持确定性和默认惩罚参数；随机采样及复杂处理器需要请求级状态恢复，后续单独实现，不能用全局 set_random_seed 假装等价。

## 7. 流式输出的提交边界与解码恢复

“生成了 token”“控制进程收到 token”和“用户应用实际收到文字”不是同一个边界。首版定义前端 CPU 日志提交为恢复边界：接受输出增量、记录 token/解码事件和文本游标，然后入 out_list、唤醒 HTTP 生成器；这几步对冻结操作保持原子顺序。

故障时，已经提交但尚未交给 HTTP 的增量保留并只发送一次；未提交的旧尝试结果作废。恢复时保留同一 HTTP 生成器及其流式偏移，不向它发送中间 finish_reason、错误终态或第二个开头。

Detokenizer 进程可能比 Tokenizer 多处理了几个结果，因此不能直接沿用其“最新” decode_status。建议保留与每次已提交输出对齐的原始 decode 增量事件及初始化元数据，恢复时在新 attempt 下静默重放到已提交边界，重建未完成 UTF-8、解码游标和上下文；重放只重建状态，不再输出旧文本。随后为新 Scheduler 输出设置正确游标。先以纯文本、EOS/长度停止验证，后续再增加自定义 stop 跨边界与解析器状态。

不能按字符串长度等同 token 个数，也不能把整个已输出文本重新编码来代替原 token。事件记录采用增量与有界检查点，避免每个 token 复制全部历史造成二次增长。解码恢复未达到一致性检查时明确失败，不删除原前缀后静默重来。

此保证限于原服务进程和连接存活：不重复向同一 HTTP 输出序列追加已提交增量。现有流式接口没有客户端逐块应用确认，不能据此宣称断线重连后的端到端 exactly-once。还需实现恢复等待心跳与读超时协同，测试代理/客户端不会因暂停而提前断开。

## 8. 超时、取消、资源与失败语义

- 请求自己的绝对超时不因重派发重置；额外重试次数与累计恢复等待均有上限。初始建议最多额外 2 次、累计恢复等待 600 秒，最终参数在实现时明确命名和校验，不把它误当现有 CLI。
- 请求期限到达只终止该请求和后续重派发，不擅自取消已经接受的集群恢复事务。集群事务与请求等待预算分别记录。
- 客户端断开、主动 abort、恢复超时之间竞争时，只允许一个终态；取消同时覆盖当前及排队的新 attempt。
- 不自动重试参数错误或无依据地循环处理 OOM。重建容量不足时按预算延后或明确失败。
- CPU 日志按总请求数、token/解码事件字节和保留时间限额；接受恢复请求前预留预算，不能中途静默淘汰活跃记录。终态回收大对象，tombstone 有数量/期限上限。
- 模型/权重版本必须一致；恢复时版本变化则明确终止本次续推，不把两版模型输出混到一个请求里。
- 原连接尚未开始响应时返回明确 HTTP 错误；SSE 已开始时发标准错误事件并结束。覆盖状态码枚举/整数两种内部形式，不能只记日志却让 curl 永久等待。
- 首版不承诺与“完全未发生故障”的运行逐 token 一致；要求保留已经输出的前缀、语义/计数正确并正常结束。成员数变化及浮点误差造成的后续输出差异需要独立精度评测。

| 3 | 非流式自动重试 | 请求协调器、恢复队列、Scheduler 恢复构造器 | 客户端一次请求，故障缩容后自动得到一次最终结果；首 token 前故障也覆盖 |

| 5 | 支持范围扩大及重复/并发验收 | 独立参数/采样/stop 状态适配 | 取消/超时、第二次故障、Unicode/stop 边界、并发预算与清理通过 |
| 后续 | 执行图与 PD | 沿用既有实施方案 | 请求恢复语义稳定后再接入新运行模式 |

recover API 的成功仍表示成员变更提交，不能改成“所有用户请求已生成完成”。请求恢复进度单独暴露。没有必要向产品接口泄露 HCCL、缓冲区地址等实现细节。

## 10. 验证与观测

本机 CPU 测试覆盖状态机和消息乱序：fault/finish/abort 顺序、旧 attempt 输出/Abort、取消与重派发竞争、未知 owner、tokenize 中故障、deadline 不重置、重复提交、解码静默重放、恢复上限和释放计数。生产实现时按仓库测试规范新增测试，本次没有创建或运行这些尚不存在的测试。

NPU 保留纯手动 Shell/curl/ps/jq 流程。实现每个批次后提供完整启动和该批验收命令，不要求用户用 Python 自动脚本。本方案不把未实现字段写进可执行 curl 命令；当前无需改变成功服务或立即故障注入。

| 实机场景 | 必须保存的证据与判断 |
|---|---|
| 长请求中主动 recover | 原请求完成、recover 提交；正常请求没有被故意 abort |
| 排空超时 | 明确超时；尚未切组，三卡仍能生成，不整体退出 |
| 首 token 前故障 | 原请求无人工重发仍结束或明确超时，不依赖坏卡通知 |
| 流式输出一段后故障 | 保存断点前 token 序号/内容，原连接在缩容后继续；最终范围连续、无重复终态 |
| 重复故障恢复 | 同一服务两轮以上；新的 attempt/epoch 生效，迟到结果被拒绝 |
| 中文、Emoji、特殊 token | 无重复/丢字符，token 游标和文本游标分别正确 |
| 取消、超时、恢复失败 | 只结束一次，不恢复取消请求，SSE 明确关闭 |
| 并发与 pinned rank | 上限内请求正常，预算不足可解释失败；不误改显式路由约束 |

每轮保存实际启动 SHA、未提交差异、完整启动环境/包元组、模型、server.log、状态与 apply 响应、恢复前后 PID、原连接输出、退出状态，以及每请求 attempt/epoch/token 区间的脱敏日志。需要检验不重复/不缺失时不能只看自然语言是否通顺；可使用 /generate 的流式 output_ids 与序号，并辅以 CPU 注入已知序列验证协议。

建议指标：暂停/重试/续推/放弃请求数、重建 Prefill token 数与耗时、恢复队列长度、CPU 日志字节、丢弃旧消息数、排空耗时、当前恢复阶段。阶段性日志不包含原始 prompt/完整输出，不用两次手动 curl 的时间差冒充恢复耗时。
