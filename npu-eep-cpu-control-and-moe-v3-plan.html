NPU EEP · Current Architecture

CPU 控制面 + MoE V3 动态缩容

当前路线不再重建 compacted topology。而是要让启动期拓扑、rank 编号、图和主要设备地址保持不变； 控制面负责发现进程退出并协调存活 rank，MoE 数据面通过 CANN V3 elasticInfoOptional 表达故障 rank，DP-attention 与其他 HCCL 通信单独排除。

固定：masked original topology 固定：DeepEP 固定：进程退出故障 主线：存活 rank CPU 元数据聚合 待证：CANN 9.0.0 V3 支持 理解实验：健康态 all-gather skip A/B

1. 当前决策

拓扑不缩短

original rank namespace、ServerArgs 和图中通信规模保持启动值；故障状态用固定长度 mask 表达。

控制与数据分开

CPU/服务控制面传递状态和恢复指令；NPU 只承担必须留在设备侧的模型数据通信。

不把 MC2 当故障检测器

进程状态、控制连接和硬件健康信息负责发现故障；算子/HCCL 报错只作为补充信号。

DeepEP 与 MC2 不是二选一

SGLang 选择 DeepEP 作为 MoE A2A backend；NPU DeepEP 的底层可以调用 CANN MoE/MC² 通算融合算子。当前要修改的是这条接口链，而不是改回 FuseEP。

4. 恢复过程

“一致确认”发生在任何新设备通信之前。恢复过程不要求 dead rank 参与，也不假装设备操作可以完全回滚。

发现 服务控制面确认某个 original rank 的进程已经退出。
暂停 关闭请求入口，通知所有存活 Scheduler 停止进入新 batch。
形成 mask 控制面生成固定长度 active mask，并使用现有 command_id 标识本次恢复操作。
存活者确认 所有存活 rank 确认相同 command_id、成员顺序与 mask。
刷新元数据 通过存活 rank 的 CPU 控制面聚合，生成 original-rank 固定宽度 Scheduler 视图。
刷新 MoE 构造 elasticInfo，更新专家布局，调用配套的 DispatchV3/CombineV3。
设备通信审计 确认 DP-attention、LM head、dense MLP、EPLB 不再等待 dead rank。
恢复或停住 全部存活 rank 成功才恢复；任何不一致或设备失败都保持暂停。

5. main 已有能力与新增工作

下表只回答三个问题：哪些能力可以直接复用、它为什么还不足以处理进程退出、以及本方案究竟新增什么。 “已有 demo”表示已经完成的前置验证，不等同于 SGLang main 原生能力。

绿色：已有，可复用 黄色：当前缺口 蓝色：需要新增
子系统 main 已有 / 已完成验证 当前缺口 本方案新增
服务控制
  • main 已有 TokenizerManager、DPC、Scheduler 之间的控制通道。
  • 前置 demo 已跑通 A1 status、A2 全 rank pause、A3 原拓扑 retry。
  • demo 的 retry 假设所有进程仍存活。
  • 尚不能根据真实进程退出或硬件状态下发缩容。
  • 在现有控制面增加进程/硬件状态、dead-rank 事件和 masked scale-down 指令。
  • 只联系存活 Scheduler；任何失败都保持暂停。
Scheduler 元数据
  • prepare_dp_attn_batch 会通过 MLPSyncBatchInfo.all_gather 同步元数据。
  • overlap schedule 默认可使用 tp_group.cpu_group（Gloo）。
  • 启动期 Gloo group 仍包含全部 original ranks；进程退出后 collective 会失败或等待。
  • inactive rank 的 fallback 是在 all-gather 返回后才填写，无法保护这次 collective。
  • 主方案复用服务控制 socket，在存活进程间 P2P 聚合，再把 dead-rank 槽位填为 IDLE/fallback。
  • 另做一次无故障 skip A/B，仅用于理解 all-gather 的调度作用，不作为容错方案分支。
MoE / DeepEP
  • SGLang 已通过 DeepEP 调用 dispatch/combine 与 low-latency 接口。
  • 公开的 sgl-kernel-npu 路径已有 V2/LowLatencyV2 包装。
  • 现有包装未暴露 rank 级 elasticInfoOptional。
  • xActiveMaskOptional 是 token mask，不能代替故障 rank mask。
  • 先确认目标 CANN/硬件确实提供 DispatchV3/CombineV3。
  • 打通 sgl-kernel-npu → DeepEP Buffer → SGLang dispatcher 的 V3 参数链路。
DP-attention 与其他 HCCL
  • 模型前向可通过 _TP.device_group 执行 all-gather、all-reduce 或 reduce-scatter。
  • EPLB 与专家刷新路径也可能包含设备 collective。
  • MoE V3 的 rank mask 只作用于配套 MoE 算子，不会自动保护这些通信。
  • 任何仍等待 dead rank 的 collective 都会阻止恢复。
  • 对目标配置做通信 trace，逐项排除 dead-rank-dependent collective。
  • 第一版收紧 attention TP、MoE TP、dense TP 等参数；无法排除的通信另行设计，不冒充已解决。
专家状态
  • main 已有 EPLB 专家位置元数据和专家分布/刷新路径。
  • 更新位置 metadata 不等于恢复 dead rank 上的专家权重。
  • 存活卡的固定专家槽位未必覆盖全部 logical experts。
  • 恢复前验证存活槽位是否覆盖全部 logical experts。
  • 需要时从副本、DRAM 或磁盘恢复权重，并保持每 rank 本地槽位数不变。

6. GPU 与 NPU：统一控制，分别适配数据面

统一的服务化能力

  • 查询服务、进程和硬件状态；
  • 关闭/开放 admission；
  • 下发 retry、pause、scale-down 指令；
  • 使用 original rank namespace 表达故障；
  • 超时、失败上报和 fail-stop 语义保持一致。

设备侧分别适配

  • GPU：验证 Mooncake active mask 对 collective 与 MoE 数据面的真实覆盖；
  • NPU：接入 CANN MoE V3 elasticInfoOptional；
  • 两侧都要分别审计 DP-attention、图捕捉和专家刷新；
  • 不能因为共享控制面，就假设底层算子具有相同容错能力。

7. 实验顺序

阶段 环境 验证内容 通过标准
1 · 接口探测 NPU 服务器 确认硬件型号、CANN 9.0.0 是否导出 DispatchV3/CombineV3，核对参数与产品约束。 获得可调用符号、精确签名和最小正常样例；不根据文档版本猜实现。
2 · 健康态通信清单 NPU 服务器 记录 Scheduler Gloo、DP hidden-state HCCL、DeepEP/MC2、EPLB 通信。 一次 decode 中每个 collective 的 group、backend、调用点和张量规模可定位。
3 · Scheduler skip 健康态 A/B NPU 服务器；所有 rank 健康 在两轮都启用 DP LM head 的同一配置下，对照 Scheduler CPU metadata all-gather 开/关，并构造不同长度的并发请求，使各 DP rank 出现 prefill、decode、idle 等不同状态。 输出正确、连续请求稳定、forward mode 与 batch 组织正确；不能只看“没有 hang”。该实验只帮助理解 skip 的影响，不改变容错主方案。
4 · MoE V3 微实验 NPU 服务器 先脱离 SGLang，验证同一通信域创建后通过 elasticInfo 剔除一个故障 rank。 存活 rank 的 DispatchV3/CombineV3 有限时间返回，结果正确，无重新编译。
5 · sgl-kernel-npu 接入 NPU 服务器 把 V3 和 elasticInfo 暴露到 DeepEP Python API，并验证正常态回归。 全 active 与 V2 结果一致；scale-down 输入在 dispatch/combine 间保持一致。
6 · 进程退出集成 NPU 服务器 推理中 kill 一个 rank，控制面暂停、形成 mask、刷新元数据与 MoE 数据面。 不等待 dead rank；所有存活 rank 一致恢复，或在限定时间内明确保持暂停。

7.1 Scheduler all-gather 理解性实验启动方式

两轮都在四个 rank 全部健康、未启用容错的情况下运行。baseline 和 skip 使用相同模型与参数， 都启用 --enable-dp-lm-head，仅切换 SGLANG_SCHEDULER_SKIP_ALL_GATHER。两轮顺序运行，不能同时占用同一组 NPU。

已确认的负例：若未启用 DP LM head，当前 Qwen3-MoE 配置需要全局 MLP token 元数据。 skip 会使 global_num_tokens_for_logprob_gpu 保持为空，随后在 logits processor 中对空值执行 torch.cumsum 并导致 Scheduler 退出。该负例说明 skip 具有严格的配置前提，不能作为通用容错方案。

8. 第一版验收

真实进程退出 不是只注入 Python 异常，也不要求故障 rank 继续参加 CPU 通信。
固定拓扑与图地址 original rank、ServerArgs、图与预分配容量不因缩容改变。
MoE 数据面避开故障卡 DispatchV3/CombineV3 使用一致 elasticInfo，存活 rank 不无限等待。
不存在漏网 collective DP-attention、LM head、dense MLP 与 EPLB 不再依赖 dead rank。
专家权重可用 metadata 更新不等于权重恢复；丢失专家必须有存活副本、DRAM 或磁盘来源。
失败时 fail-stop 恢复中任何不一致、超时或设备错误都不得重新开放推理。

9. 当前未决问题

接口与硬件

  • 实际 NPU 是 Atlas A2 还是 A3 产品系列；
  • CANN 9.0.0 安装包是否包含可用的 MoE V3 动态缩容实现；
  • DeepEP normal、low-latency、fused 三条路径分别对应哪组 V3 接口；
  • 故障进程退出后，存活 rank 上正在执行的旧算子如何有限时间结束。

SGLang 热路径

  • 存活 rank 的控制面聚合需要同步哪些 Scheduler 字段；
  • 控制面聚合的一致性与每步延迟是否可接受；
  • DP-attention gather/reduce 是否能通过参数组合完全消除；
  • MoE 专家刷新是否包含 WORLD/TP collective，权重恢复来源是什么。
